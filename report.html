GG Bond: A Virtual Pet Growth Platform

Ming Zhao
Department of Computer Science, University of Auckland, New Zealand
mzha585@aucklanduni.ac.nz
Abstract
This report describes GG Bond (also called Doggy Growth Plan), a full-stack web application where users can adopt and raise virtual dogs. The project was built by a team of six students for COMPSCI 732. The system includes pet feeding and training, health tracking, an AI pet health advisor powered by large language models, Google Maps for finding nearby pet services, a peer-to-peer marketplace for pet items, real-time chat between users, community posts, an achievement and reward system, and support for four languages (English, Chinese, Japanese, and Te Reo Māori). The frontend uses React 18 with React Router and Framer Motion. The backend uses Node.js with Express, and the database is MySQL 8.0. Authentication is handled by Firebase with a local fallback. My main contributions were the entire backend server and database design, the marketplace and chat systems, the admin dashboard, the AI advisor integration, and the deployment infrastructure. The project shows that a simple three-tier architecture with a relational database can deliver a feature-rich, multi-user web application suitable for real-world use.
Keywords: virtual pet, full-stack web application, React, Express, MySQL, AI advisor, Google Maps, internationalisation

I. Introduction

Virtual pets are not a new idea. From Tamagotchi in the 1990s to mobile games like Neko Atsume today, people enjoy looking after a digital companion. The basic loop is simple: you feed it, train it, and watch it grow. In this project, we brought this idea to the modern web. Our platform, GG Bond, lets users adopt a virtual dog and take care of it through many different activities.

This project was done for COMPSCI 732 (Software Tools and Techniques) at the University of Auckland. Our team has six members: Huanhuan Li, Jiayi Lyu, Xiang Zhang, Ming Zhao, Xingyan Zhou, and Kejun Xu. We set three clear goals at the start:

  • Build a working web application that runs on the public internet, not just on localhost.
  • Connect to external services like AI (for pet health advice) and Google Maps (for finding pet shops and vets).
  • Support multiple users at the same time, with all data saved in a real database.

In this report, I focus on my own individual contributions. I was mainly responsible for the backend server, the MySQL database design, the marketplace feature, the chat system, the admin dashboard, the AI advisor integration, and the deployment setup. I will explain what I built, how I built it, and what problems I faced along the way.

II. Related Work

Virtual pet platforms have a long history in gaming. Neopets, launched in 1999, was one of the first popular web-based virtual pet sites. It let users adopt pets, play games, earn currency, and trade items in a marketplace [1]. Flight Rising is a similar platform focused on collecting and breeding dragons [2]. On mobile, games like Neko Atsume and Tamagotchi showed that simple care mechanics can be very engaging. Research by Banks and Humphreys [3] found that virtual worlds and social play are key drivers of user engagement, which guided our decision to add community features.

Our project differs from these in several important ways. First, we built it as a responsive web application using modern frameworks (React, Express), not as a traditional game site. Second, we integrated an AI-powered health advisor that uses large language models to give real, contextual pet care advice [4]. This is much more useful than a static FAQ. Third, we used Google Maps to connect the virtual experience to the real world — users can find actual pet shops, vets, and parks near them [5]. Fourth, our four-language support (including Te Reo Māori) reflects New Zealand's bicultural context, which is unique among pet platforms.

For the tech stack, we chose React, Express, and MySQL. This is similar to the popular MERN stack [6], but we replaced MongoDB with MySQL. The reason is that our data has many relationships: users own pets, pets have achievements, marketplace listings belong to users, and messages connect two users. A relational database with foreign keys handles these relationships better than a document store [7].

III. Design

A. Software Architecture

The system follows a three-tier architecture (Fig. 2). The frontend is a React 18 single-page application using React Router v6 for navigation and Framer Motion for animations. It communicates with the backend through HTTP requests to a REST API. The backend is a single Node.js/Express server that handles all business logic. Data is stored in MySQL 8.0, accessed through the mysql2 library with a connection pool of 10 connections.

For authentication, we used Firebase Auth (email and password). However, we found that Firebase sometimes has connection problems, especially in our testing environment. So I built a backup login system that stores hashed passwords in our own MySQL database. If Firebase is down, the app automatically switches to the local login. This dual-auth approach made the system much more reliable.

We chose a single monolithic server instead of microservices. For a six-person team, one server is much simpler to develop, test, and deploy. All API endpoints are in one file (index.js, about 1,100 lines), organised by feature: auth, pet, marketplace, chat, community, admin, AI, and map.

Fig. 2. Entity-Relationship diagram of the database. The two core tables (users, pets) connect to seven functional modules: Pet Care, Training, Achievements, Rewards, Marketplace, Inventory, and Chat.

B. Database Design

The MySQL schema is normalised to third normal form. Two core tables — users and pets — have a one-to-one relationship. From these, seven modules extend:

  • Pet Care: pet_activities (feeding, walking, playing) and health_records (vet visits, medication).
  • Training: training_skills (skill definitions) and pet_training_progress (per-pet progress).
  • Achievements: achievements (definitions) and pet_achievements (unlock records).
  • Rewards: daily_rewards (reward templates) and user_reward_claims (claim history).
  • Marketplace: marketplace_listings (items for sale or free).
  • Inventory: inventory (items owned by each user).
  • Chat: conversations and messages.

A key design pattern is "template-record separation." For achievements, rewards, and training skills, the available items are defined in a template table, and each user's progress is stored in a separate record table. This makes it easy to add new content (like a new achievement) without changing any code.

C. User Interface

The app has 15 screens. On mobile, a bottom navigation bar provides access to all pages. On desktop (above 768px), a sidebar replaces the bottom bar. The main screens are: Home (pet view), AI Advisor, Map, Community, Profile, Marketplace, Inventory, Leaderboard, Health Records, Achievements, Daily Rewards, Training, Messages, and Admin. CSS Flexbox handles the responsive layout. Framer Motion provides smooth page transitions and pet reaction animations.

Fig. 3. Achievement system showing unlocked badges and progress tracking.

D. Why This Design

We made three important design decisions and here is why. First, MySQL over MongoDB — our data is highly relational (users own pets, pets have many achievements, marketplace listings belong to users). Foreign keys and joins keep the data consistent, which is hard to do in a document database. Second, Firebase with a local fallback — Firebase is easy to set up and handles password hashing for us, but it is not always reliable. Having a backup login saved us during demos. Third, one server file — this was a practical choice. It made deployment simple (just one file to run), though for a bigger project we would split it into modules.

IV. Implementation

A. Backend Server

I wrote the entire backend in backend/src/index.js (about 1,100 lines). The server uses Express with CORS enabled and JSON body parsing (25MB limit for base64 image uploads). A MySQL connection pool of 10 connections handles concurrent requests. I created several helper functions that are used throughout the codebase:

  • parseJsonField() — safely reads JSON columns, returning a fallback if the value is null or invalid.
  • toIso() and toDateOnly() — normalise date formats from MySQL to JavaScript.
  • ensureTrainingState() and ensureRewardsState() — lazily initialise per-user data rows on first access.
  • defaultAchievementCounters() — sets up 13 tracking metrics (feed_count, exercise_count, etc.) for new users.

When a new user signs up, they automatically receive a default inventory of 10 items (dog food, toys, medicine, accessories) and 9 training skills (sit, shake, lie down, stay, come, roll over, play dead, math, fetch). This makes the app feel complete from the very first login.

B. Marketplace System

The marketplace lets users list pet-related items for sale or for free. I built both the backend API endpoints and the frontend page (970 lines of React). Users can upload images, which are stored as base64 data URIs in MySQL TEXT columns. This is simple and avoids needing a separate file storage service, though it uses about 30% more space than the original file.

The marketplace supports search and filter by category (food, toy, medicine, accessory) and listing type (sale, adoption, free). A significant bug I fixed was a MySQL "sort buffer" error: when the listings table grew past a few hundred rows, the ORDER BY query crashed. I solved this by removing the SQL sorting and doing it in JavaScript after the query. This works fine for our scale, but would need database-level pagination for a production system.

Fig. 4. Marketplace with category filters, listing types, and image upload support.

C. Chat and Community

The chat system allows one-to-one conversations between users. The database has a conversations table (storing the two participant UIDs) and a messages table (sender, content, timestamp, read status). When a user sends their first message to another user, the system creates a new conversation if one does not already exist. The frontend polls for new messages every 3 seconds. Unread counts are calculated from the last-read timestamp per conversation.

The community page is a simple social feed. Users can post updates about their pets, like posts, and leave comments. I stored the like count as a denormalised integer on the community_posts table, rather than using a separate likes junction table. This is faster for reading (which happens much more often than writing), at the cost of not being able to track who liked what.

D. Admin Dashboard

I built an admin dashboard (790 lines) with management interfaces for users, pets, marketplace listings, and system statistics. The admin API includes user search/filter, pet status editing, listing moderation, and aggregate queries (total users, active pets, marketplace volume). Access control checks the user's role field in the database; non-admin users are redirected.

Fig. 5. Admin dashboard showing user management, search/filter, and system statistics.

E. AI Health Advisor

The AI advisor lets users ask questions about their pet's health. It uses Groq as the main LLM provider and Moonshot as a fallback. The AI plays "Dr. Pawsome," a friendly pet doctor persona. A critical implementation challenge was language control: we support English, Chinese, Japanese, and Māori, and the AI must respond in the user's selected language. I solved this by placing explicit language instructions at both the beginning and end of the system prompt, which dominates the English-language context. A client-side Gemini fallback activates when the backend is unreachable, so the feature degrades gracefully.

Fig. 6. AI health advisor "Dr. Pawsome" providing contextual pet care advice in the user's language.

F. Google Maps Integration

The map page (656 lines) integrates the Google Maps JavaScript API with the Places library. It shows nearby pet-related locations: parks, veterinary clinics, and pet stores. The default centre is Auckland, New Zealand (-36.8485, 174.7633). Users can check in at locations, with data saved both locally (localStorage for offline access) and on the server. The implementation uses google.maps.places.PlacesService for nearby search.

G. Internationalisation

We support four languages through a custom React context (I18nContext). Translation files (en.js, zh.js, ja.js, mi.js) provide key-value mappings. The useI18n() hook exposes a t(key) function. I connected the translation system to multiple pages and replaced many hardcoded Chinese strings with proper t() calls.

H. Deployment and Operations

I deployed the application on a Linux virtual machine with Nginx as a reverse proxy. The React frontend is built with react-scripts build and served as static files. The Express backend runs as a systemd service with automatic restart on crash. I set up automated daily MySQL backups using cron and mysqldump with 7-day retention. The database uses a dedicated ggbond_app user with limited privileges, following the principle of least privilege.

VI. Methodology

We used a lightweight Agile approach. All code was managed on GitHub using feature branches and pull requests. Work was divided by feature module: I owned the backend architecture, marketplace, chat, community, admin, AI integration, and deployment. Other team members owned the pet visual system, training, achievements, map UI, profile, and inventory frontend pages.

We met once a week in person and used a WeChat group for daily communication. The README served as our main documentation, updated continuously as features were completed. We wrote it in both English and Chinese so all team members could read it. Our development workflow was: (1) implement on a local branch, (2) test locally, (3) push to GitHub, (4) deploy to the production server, (5) verify in production. This kept the live demo current throughout the project, which was valuable for our team seminar presentation.

The biggest methodology challenge was coordination. With six developers, merge conflicts were frequent, especially in shared files like App.js and index.js. In hindsight, we should have established clearer file ownership from the beginning.

VII. Tooling

A. Development Tools

Git and GitHub. We used Git for version control with over 150 commits across all team members. Pull requests helped us review code before merging. The commit history provides a clear audit trail of what was added and fixed. GitHub Issues was used occasionally for bug tracking.

Node.js and npm. The frontend has 18 dependencies and the backend has only 4 (express, cors, dotenv, mysql2). Keeping dependencies minimal reduces security risk and makes the project easier to understand.

VS Code. All team members used VS Code as their main editor. The integrated terminal and Git support made the development workflow smoother.

B. AI-Assisted Development

I used Claude (by Anthropic) extensively during this project. It helped with three main tasks:

  • Code generation: Claude generated the first version of the marketplace page, the admin dashboard, and the chat system. I then modified the code to fit our project's specific needs and style.
  • Debugging: When I encountered the MySQL sort buffer error, Claude helped me understand the root cause and suggested sorting in JavaScript as a workaround.
  • Documentation: Claude helped structure the README and provided drafts for this report.

Drawbacks of AI tools. The code from Claude was not always correct. For example, it did not know that mysql2 returns query results as [rows, fields] (an array), not just rows. This caused a subtle bug that took me time to find. Also, if I relied on AI too much, I would not truly understand the code. I made a rule to read every line before committing. Sometimes the AI suggested overly complex solutions when a simpler approach would work better. For instance, it once suggested using a WebSocket library for the chat, when simple HTTP polling was perfectly fine for our use case.

Overall effectiveness. For repetitive tasks like building a CRUD page or writing API endpoints, Claude could generate a working draft in minutes. I estimate it saved about 40–50% of my time on those tasks. However, for tricky bugs, architecture decisions, and understanding system-level issues, I still had to think and decide myself. AI is a powerful tool, but it is not a replacement for understanding.

C. Server and Deployment Tools

Nginx serves the React build and forwards /api requests to Express. systemd keeps the backend running with automatic restart on failure. cron + mysqldump runs daily database backups with 7-day retention. These tools are simple but reliable, which is important for a student project deployed in production.

VIII. Discussion

A. Goals Achieved

We achieved all three goals. The application has 15 working screens and is deployed on a real server accessible from any browser. The AI advisor and Google Maps integration work correctly. Multiple users can use the system simultaneously with data persisted in MySQL. The project went beyond the original proposal by adding features like the achievement system, daily rewards, leaderboard, and four-language support.

B. Problems Encountered

Firebase authentication instability. Firebase occasionally failed to connect, preventing users from logging in. The solution was a dual-auth system: Firebase as primary, MySQL-backed local auth as fallback. This added complexity but made the app much more reliable. The lesson: never depend on a single external service for something as critical as login.

MySQL performance. The marketplace ORDER BY query caused "Out of sort memory" errors when the table exceeded a few hundred rows. I fixed this by sorting in JavaScript after the query. This is pragmatic but not scalable — a proper solution would add database indexes and tune sort_buffer_size.

Image storage. Storing images as base64 in MySQL TEXT columns uses about 30% more space due to encoding overhead. For a real product, we would use cloud object storage like AWS S3 or Cloudinary.

Team coordination. Six developers working on the same codebase caused frequent merge conflicts. We should have split the backend into separate files by feature from the beginning, and assigned clear file ownership to each team member.

C. Architectural Reflections

The monolithic backend (one 1,100-line file) was appropriate for our project's scope but would not scale. If I were to rebuild it, I would use Express Router to split endpoints into separate files by feature. The template-record database pattern was a good choice — it made adding new achievements and rewards trivial. The dual-auth system was the most valuable architectural decision, as it ensured the app worked even when external services failed.

IX. Conclusion

This project taught me how to build and deploy a full-stack web application from scratch. GG Bond is a working virtual pet platform with AI health advice, location-aware services, a marketplace, chat, community features, and four-language support. It uses a straightforward but effective architecture: React frontend, Express backend, MySQL database.

The key lessons I learned are: (1) choose the right database for your data model — MySQL's relational model was the correct choice for our complex entity relationships; (2) always build in fallbacks — the dual-auth system saved us during demos and in production; (3) AI coding tools are helpful but require careful review — they can introduce subtle bugs if you trust them blindly; (4) good documentation from the start makes teamwork much smoother and reduces onboarding time for new members.

If I could start over, I would: add automated tests from day one (Jest for units, Cypress for E2E), use a dedicated file storage service for images, split the backend into feature-based modules, and implement WebSocket for real-time chat instead of polling. Future work could include a React Native mobile app, image-based AI symptom analysis, and gamification improvements like pet evolution stages.
