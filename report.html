GG Bond: A Virtual Pet Growth Platform

Ming Zhao
Department of Computer Science, University of Auckland, New Zealand
mzha585@aucklanduni.ac.nz
Abstract
This report describes GG Bond (also called Doggy Growth Plan), a full-stack web application where users can adopt and raise virtual dogs. The project was built by a team of six students for COMPSCI 732. The system includes features like pet feeding, training, health tracking, an AI pet health advisor, Google Maps for finding nearby pet services, a marketplace for pet items, real-time chat, and support for four languages. The frontend uses React 18, the backend uses Node.js with Express, and the database is MySQL 8.0. My main contributions were the backend server and database design, the marketplace and chat systems, the admin page, the AI advisor integration, and the deployment setup. The project shows that a simple three-tier architecture can build a working, multi-user web application with many features.
Keywords: virtual pet, full-stack web application, React, Express, MySQL, AI advisor, Google Maps, internationalisation

I. Introduction

Virtual pets are not new. From Tamagotchi in the 1990s to mobile games today, people enjoy looking after a digital companion. The idea is simple: you feed it, train it, and watch it grow. In this project, we brought this idea to the web. Our platform, GG Bond, lets users adopt a virtual dog and take care of it through different activities like feeding, walking, training, and going to the vet.

This project was done as part of COMPSCI 732 (Software Tools and Techniques) at the University of Auckland. Our team has six members: Huanhuan Li, Jiayi Lyu, Xiang Zhang, Ming Zhao, Xingyan Zhou, and Kejun Xu. We set three goals: first, build a real web application that works on the internet; second, connect to outside services like AI and Google Maps; third, make the system support multiple users at the same time with persistent data.

In this report, I focus on my own work. I was mainly responsible for the backend server, the MySQL database, the marketplace feature, the chat system, the admin dashboard, the AI advisor, and the deployment. I will explain what I did, how I did it, and what problems I ran into.

II. Related Work

Virtual pet games have a long history. Neopets [1], launched in 1999, is one of the most well-known. It lets users adopt pets, play games, and trade items. Flight Rising [2] is another example, focused on collecting and breeding dragons. On mobile, games like Neko Atsume show that simple pet care can still be very popular.

Our project is different in a few ways. First, we built it as a responsive web app, not a mobile app. Second, we added an AI advisor that gives real pet health advice using a large language model. This is more useful than a static FAQ page. Third, we used Google Maps to show nearby pet shops, vets, and parks. This connects the virtual pet to the real world. Fourth, we support four languages including Te Reo Māori, which reflects the culture of New Zealand.

For the tech stack, we used React, Express, and MySQL. This is similar to the common MERN stack [4], but we chose MySQL instead of MongoDB. The reason is that our data has many relationships (users, pets, items, achievements), and a relational database handles this better with foreign keys and joins.

III. Design

A. Software Architecture

The system has three layers. The frontend is a React single-page application with React Router for navigation. It talks to the backend through HTTP requests. The backend is a Node.js/Express server that handles all the business logic. The database is MySQL 8.0, connected through the mysql2 library. For login, we use Firebase Authentication, but we also built a backup login system using our own database because Firebase sometimes has connection issues.

We chose a single server instead of microservices. For a team of six, one server is much easier to manage. All the API endpoints are in one file (index.js, about 1,100 lines), organised by feature.

Fig. 2. Entity-Relationship diagram showing the database schema with users, pets, marketplace, inventory, achievements, training, and chat tables.

B. Database Design

The database has two main tables: users and pets. Each user has one pet (1:1 relationship). From these, seven modules extend: Pet Care (pet_activities, health_records), Training, Achievements, Rewards, Marketplace, Inventory, and Chat. For features like achievements and training skills, we use a "template-record" pattern — the available achievements are defined in one table, and each pet's progress is stored in another. This way we can add new content without changing the code.

C. User Interface

The app has 15 screens. On mobile there is a bottom navigation bar; on desktop there is a sidebar. The main screens are: Home (pet view), AI Advisor, Map, Community, Profile, Marketplace, Inventory, Leaderboard, Health Records, Achievements, Rewards, Training, Messages, and Admin. We used CSS Flexbox for layout with a responsive breakpoint at 768px. Framer Motion provides smooth page transitions and pet animations.

D. Why This Design

We made a few important decisions. First, MySQL over MongoDB — our data is relational, with users owning pets and pets having many achievements. Foreign keys keep the data consistent. Second, Firebase with a fallback — Firebase is easy to set up but not always reliable, so we added a local login option. Third, one server file — this made deployment simple, though it would need refactoring for a bigger project.

IV. Implementation

A. Backend Server

I wrote the entire backend in backend/src/index.js (about 1,100 lines). The server uses Express with CORS and JSON parsing (25MB limit for image uploads). A MySQL connection pool of 10 connections handles concurrent requests. I created helper functions: parseJsonField() for reading JSON columns, toIso() for dates, and ensureTrainingState() for creating default training data for new users.

When a new user signs up, they automatically get 10 inventory items (dog food, toys, medicine) and 9 training skills (sit, shake, lie down, stay, come, roll over, play dead, math, fetch). This makes the app feel alive from the first login.

Fig. 3. The marketplace where users list pet items for sale or free adoption.

B. Marketplace

The marketplace lets users list pet items for sale or for free. I built both the API and the frontend page (970 lines). Users can upload images, stored as base64 strings in MySQL. This is simple and avoids needing a separate file server. The marketplace supports search and filter by category (food, toy, medicine, accessory) and type (sale, adoption, free).

I had a problem with MySQL when the table grew. The ORDER BY query caused a "sort buffer" error. I fixed this by removing the SQL sorting and doing it in JavaScript instead. This works fine for hundreds of records, but would need a better solution for millions.

C. Chat and Community

The chat system allows two users to send messages. The database has conversations and messages tables. When a user sends a first message, a new conversation is created if one does not exist. The frontend polls every 3 seconds for new messages.

The community page is like a simple social feed. Users can post updates, like posts, and leave comments. I stored the like count directly on the post table for faster reads.

Fig. 4. Admin dashboard for managing users, pets, and marketplace listings.

D. Admin Dashboard

I built an admin page (790 lines) where administrators can manage users, pets, and marketplace listings. The page shows statistics like total users and active pets. Only users with the "admin" role can access it. I added search and filter functions for finding specific records quickly.

Fig. 5. AI pet health advisor powered by Groq/Moonshot LLMs.

E. AI Health Advisor

The AI advisor lets users ask questions about their pet's health. It uses Groq as the main provider and Moonshot as a backup. The AI plays "Dr. Pawsome," a friendly pet doctor. One tricky part was making the AI respond in the right language. We support English, Chinese, Japanese, and Māori. I put the language instruction at both the top and bottom of the prompt so the AI knows which language to use. A client-side Gemini fallback activates when the backend is down.

Fig. 6. Google Maps integration showing nearby pet services with check-in feature.

F. Google Maps and i18n

The map page shows nearby pet places (parks, vets, pet stores) using the Google Maps Places API. Users can check in at locations. Data is saved both locally and on the server. We support four languages through a React context with a t(key) function. I connected the translation system to several pages and replaced hardcoded Chinese strings with translation keys.

G. Deployment

I deployed the app on a Linux server with Nginx. The frontend is built with react-scripts build and served as static files. The backend runs as a systemd service (auto-restart on crash). I set up daily MySQL backups via cron with 7-day retention.

V. Testing

We tested everything by hand — no automated tools like Jest or Cypress. Here is what we did:

  • API testing: Every endpoint was tested with curl and browser developer tools, checking responses and error handling.
  • Cross-browser: Checked on Chrome, Firefox, and Safari.
  • Mobile: Used Chrome DevTools to simulate phone sizes (320px, 375px, 768px, 1024px).
  • Database: Manually tested foreign keys by creating and deleting related records.
  • Error cases: Tested Firebase downtime, slow APIs, and invalid input.

We kept a testing checklist in the README covering all 15 screens. Automated tests would have been better, but our manual process was systematic.

VI. Methodology

We used a simple Agile process. All code was on GitHub with feature branches and pull requests. Work was divided by feature: I handled the backend, marketplace, chat, community, admin, AI, and deployment. Others worked on pet visuals, training, achievements, map UI, profile, and inventory.

We met once a week in person and used WeChat for daily chat. The README was our main documentation, written in both English and Chinese. Our workflow: write code locally, test, push to GitHub, deploy, verify. This kept the live demo current throughout the project.

VII. Tooling

A. Development Tools

Git and GitHub. Over 150 commits from all members. Pull requests helped with code review. The commit history is a clear record of what was added and fixed.

Node.js and npm. The frontend has 18 dependencies, the backend only 4 (express, cors, dotenv, mysql2). Fewer packages means less security risk.

VS Code. Everyone used it as their main editor.

B. AI Tools

I used Claude (by Anthropic) a lot during this project. It helped with three things:

  • Writing code: Claude generated the first version of the marketplace, admin dashboard, and chat. I then changed the code to fit our project.
  • Finding bugs: When MySQL had the sort buffer error, Claude helped me understand the problem and suggested sorting in JavaScript.
  • Writing docs: Claude helped with the README and this report.

Drawbacks. The code from Claude was not always correct. For example, it did not know that mysql2 returns results as [rows, fields], not just rows. I had to fix this by hand. If I relied on AI too much, I would not understand the code myself. I made sure to read every line before committing. Sometimes the AI gave complicated solutions when a simple one would work.

Overall effect. For repetitive tasks like building a CRUD page, Claude could generate a working draft in minutes. I estimate it saved about 40–50% of my time on those tasks. But for tricky bugs and architecture decisions, I still had to think and decide myself.

C. Server Tools

Nginx serves the frontend files and forwards API requests to Express. systemd keeps the backend running with auto-restart. cron + mysqldump runs daily database backups with 7-day retention.

VIII. Discussion

A. Goals Achieved

Yes, we achieved all three goals. The app has 15 working screens. It is deployed on a real server and accessible from any browser. The AI advisor and Google Maps work. Multiple users can use it at the same time with data saved in MySQL.

B. Problems

Firebase login. Sometimes Firebase could not connect. We added a backup login using our own database. This made the app much more reliable.

MySQL sorting. With many marketplace listings, the ORDER BY was too slow. We sorted in JavaScript instead. Fine for now, but not a long-term solution.

Image storage. Base64 in MySQL uses 30% more space than the original file. For a real product, we would use AWS S3 or Cloudinary.

Team coordination. Six people on the same code meant frequent merge conflicts. We should have divided files more clearly from the start.

C. Architecture Lessons

One big server file worked at first but became hard to manage. Next time, I would split the backend into separate files by feature from the beginning. The template-record database pattern was a good choice — it made it easy to add new achievements and rewards without code changes.

IX. Conclusion

This project taught me a lot about building a full-stack web application. GG Bond is a working virtual pet app with AI advice, maps, a marketplace, and chat. It uses a simple but effective architecture: React frontend, Express backend, MySQL database.

Key lessons: (1) choose the right database for your data — MySQL was correct because our data has many relationships; (2) always have a backup plan — the Firebase login fallback saved us many times; (3) AI tools are helpful but you must check their work carefully; (4) good documentation makes teamwork much smoother.

If I could do this again, I would add automated tests from the start, use a file storage service for images, and split the backend into smaller files. Future work could include WebSocket for real-time chat, React Native for a mobile app, and image-based AI diagnosis.
